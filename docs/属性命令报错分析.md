# GeoGebra 属性命令报错分析整理（Set* / Show* / style op）

> 对象属性设置命令的常见报错根因梳理与防御层缺口分析。
> 相关代码：`src/lib/ggbBridge.ts`（style op）、`src/lib/toolExecutor.ts`（set_style）、
> `src/lib/commandValidate.ts`（静态预检）、`src/lib/ggbKB.ts`（RAG 知识库）、`src/lib/schema.ts`（Zod 校验）。

## 1. 范围与三条执行路径

"设置对象属性"在这个项目里有三条独立路径，报错行为**各不相同**：

| 路径 | 入口 | 属性载体 | 失败可见性 |
|---|---|---|---|
| ① JSON 流水线 style op | `ggbBridge.executeOne` case "style" | 结构化字段（color/thickness/visible/opacity/dashed/pointSize/pointStyle） | 原生 setter 返回 void，失败不可见（本轮已加 exists 预检 + opacity 可观测） |
| ② eval 命令 | `ggbBridge.executeOne` case "eval" | `SetColor(obj, r,g,b)`、`SetFilling(obj, 0.3)` 等 GGB 脚本命令 | 引擎只回一句 `evalCommand 返回 false`，无语义 |
| ③ Agent set_style 工具 | `toolExecutor` dispatch case "set_style" | 结构化字段（同 ①） | 有 exists 预检，报「对象 X 不存在」 |

三条路径共享的上游：schema 校验（防漂移第 4 层）→ RAG 纠正（第 6 层）→ 执行层（第 7 层）。
但 eval 路径独有 commandCorrect/batchCorrect 纠正；style op 路径独有 Zod 值域约束——**两层互不覆盖对方的盲区**。

## 2. 六大错误模式

### 模式 A：命令不存在 / 臆造

**现象**：AI 生成 GeoGebra 根本不存在的属性命令。

| 臆造命令 | 正确替代 | 现有拦截 |
|---|---|---|
| `SetOpacity(obj, 0.5)` | `SetLineOpacity` | 硬黑名单（`GGB_FORBIDDEN_COMMANDS`）→ schema 层直接拒绝 → 格式修复循环 |
| `SetTransparency` | `SetLineOpacity` | 同上 |
| `SetOpaque` | `SetLineOpacity` | HALLUCINATION_MAP 映射，纠正器自动改写 |
| `PauseAnimation` / `StopAnimation` | `SetAnimating(obj, false)` | 映射建议（带括号形态不自动替换，只给建议） |
| `SetColour`（拼写变体） | `SetColor` | Levenshtein ≤2 模糊纠正，距离 1 自动改写 |

**根因**：透明度/动画类语义在 GeoGebra 命令名里最不直观（线透明度叫 `SetLineOpacity` 而非 `SetOpacity`）。

**历史缺口（本轮已修）**：`SetAnimating` 被 HALLUCINATION_MAP 当作"正确命令"推荐，却不在 `GGB_COMMAND_DEFS` 里——
纠正器把它替换出来之后，下一轮又会被同一纠正器报「不在已验证命令库」，**来回震荡**。
修复：KB 补录 `SetAnimating(obj, flag)` 条目（滑块/动画组，2d+3d）。

### 模式 B：模式相关（3D 禁令）—— 静态层最漏洞

**现象**：3D 模式下生成 2D 专用命令，引擎一句 false，AI 看不到原因，下一轮继续犯。

**3D 禁用清单（9+1 条，三方一致：prompts MODE_3D_ADDON / commands 白名单文本 / ggbKB modes 字段）**：

| 命令 | 3D 下的行为 | 替代方案 |
|---|---|---|
| `SetFilling(obj, n)` | 对立体无效 | style op 的 `opacity` 字段 |
| `SetPointSize(obj, n)` | 不可用 | `Sphere(P, 0.2)` 标记点 |
| `SetPointStyle(p, n)` | 不可用（KB 标注仅 2D） | 删除 |
| `SetCaption(obj, text)` | 不可用 | `Text("<文字>", 点)` |
| `ShowLabel(obj, bool)` / `SetLabelMode(obj, n)` | 不可用 | 删除 |
| `Rename(obj, name)` | 不可用 | 创建时直接命名 |
| `SetViewDirection(dir)` | 纯 3D applet 完全不可用 | 鼠标旋转 |
| `SetAxesRatio(x,y[,z])` | 不可靠 | view op |
| `ZoomIn([scale])` | 常返回 false | view op |

**根因**：禁令此前**纯 prompt 级**——
- `findCommand()` 查 KB 时不感知 mode（3D 下 `SetFilling` 照样精确命中）；
- `commandValidate` 无 mode 参数；
- `buildHallucinationWarnings` 的 3D 过滤列表引用的 9 个命令在 MAP 中无条目（死过滤，实际只靠硬拼的 modeNote 文案）。

于是命令顺利穿过所有静态层，直到引擎才失败，且只得到无语义的 `GGB evalCommand 返回 false`。

**处置（本轮已修）**：`validateGGBCommand(cmd, mode?)` 增加 mode 参数，3D 下对禁令清单直接拦截，
报错带替代方案（数据源优先取 ggbKB 的 `note`，兜底 `MODE_3D_FORBIDDEN` 表）。
mode 经 `ggbBridge.executeOne`（executeCommands 已持有 appMode）与 `toolExecutor.executeToolCall`（新增透传）注入。
`buildHallucinationWarnings` 死过滤同步清理。

### 模式 C：参数与值域错误

**现象与根因**（按高频排序）：

1. **SetColor 的数值语义（2026-09 实测修正：原判断方向相反）**：
   `SetColor(obj, r, g, b)` 的 r/g/b 官方语义是 **0~1 浮点**，引擎内部按 ×255 解析。
   5.4.927 实测（XML 读回 objColor）：`SetColor(c, 0.9, 0.2, 0.2)` → rgb(229,51,51) ✅ 正确；
   `SetColor(c, 230, 50, 50)` → rgb(255,255,255) ❌ 全白（>1 的整数全部分量被钳成 255）。
   此前记录的「0.9→230」恰是 0~1×255 的**正确换算**，被误读成了误用证据；
   当年判「❌」的真实原因大概率是 Set* 命令恒返回 false 被当成了失败（见模式 B 的 isScriptingCommand 豁免）。
   真正的高频坑是反方向的：AI 受 CSS 习惯影响写 0~255 整数 → 静默渲染成白色。
2. **透明度与 RGB 值域混淆**：`SetLineOpacity(c, 50)` ❌（应 0~1）。
   修正后 SetColor 与透明度值域一致（都是 0~1），不再有方向相反的混淆。
3. **颜色名形态**：`SetColor(c, "红色")` ❌（GGB 不识别中文色名）；
   `SetColor(c, red)` ❌（裸标识符被当作对象引用，必失败）。
   合法形态：英文字符串 `"red"`（或 `"#RRGGBB"`）或 4 参 0~1 浮点 RGB。
4. **参数个数**：`SetLineStyle(c)` 缺参。KB `paramCount` 只被流水线的 `batchCorrect` 用（仅 eval op），静态预检层 `ARG_COUNT_HINTS` 此前零 Set* 条目。
5. **style op 颜色格式**：必须 `#RRGGBB`（Zod `^#[0-9a-fA-F]{6}$` 拦截）——这条是三层里唯一早就有代码级校验的。

**处置（本轮已修）**：`commandValidate` 新增属性命令专项检查（仅对 KB 已收录的 Set*/Show*/Rename 生效，只查字面量、表达式放行）：
- `value-range`：SetColor 分量超出 0~1（带 ÷255 换算提示，如 230→0.902）/ 负值；SetLineOpacity、SetFilling 第二参超出 0~1；SetColor 2 参形态收到数字。
- `color-name`：中文色名 / 裸标识符色名。
- `arg-count` 回退：KB `paramCount` 兜底（`SetCoords` 豁免——3D 有官方四参重载，KB 只录了 2D 三参）。

### 模式 D：对象不存在 / 静默失败 —— 修复回路全盲

**现象**：AI 引用一个不存在的对象名（拼错、大小写不符、或引用了被回滚的对象）设置样式，画布毫无反应。

**根因**：GGB 原生 setter（`setColor`/`setLineThickness`/`setVisible`…）对不存在的对象**静默 no-op** 且返回 void。
style op 此前没有 `exists` 预检（对比同文件 animate/trace/delete 都有），恒返回 `ok:true` →
`collectFailures` 永远看不到失败 → **修复回路、熔断、known_traps 全部不触发**。

Agent 路径（set_style）有预检，报「对象 X 不存在」——但该错误前缀「执行前检查失败：」被 agentLoop
归类为"可修正"，会清零熔断计数，AI 反复犯也不熔断（有意的取舍：给模型自我修正机会，但属性名拼错可能循环多次）。

**处置（本轮已修）**：style op 加 exists 预检，目标不存在返回 `ok:false`（进 collectFailures → checker prompt 修复回路，
配规则 10 的「先创建再设置 / 核对大小写」指引）。

### 模式 E：语义混淆 —— 透明度双轨制

**现象（历史真实 bug，commit f990a47）**：审查环节误报「对象透明度为零/全透明」。

**根因**：GeoGebra 的"透明度"是**两个独立属性**：
- `SetLineOpacity` = 线条透明度（无原生 API，只能 evalCommand）；
- `getFilling` = **填充**透明度，且**无填充时默认 0**——0 不代表对象不可见！

快照曾把 `getFilling()===0` 输出成 `opacity=0.00`，模型读到快照就误判全透明。
修复后的 `readOpacity()` 改为解析 `getXML` 的 `lineOpacity`/`fillOpacity`（0-100），快照只输出非默认值。

**重大特性（2026-09-12 视觉回归对照实验发现）**：GGB 的 `evalCommand` 对**不产生新对象的
scripting 命令**（Set*/Show*/ZoomIn/Delete 等）**即使执行成功也返回 false**——实测 SetColor
后 getColor 已从 #4D4DFF 变为 #FF0000，返回值仍是 false（5.4.927 本地 bundle 与 5.4.929 CDN 一致）。
由此曾产生两个连带 bug：
1. eval 路径的 Set* 命令被误判失败 → collectFailures 收集 → 修复回路空转 + 3 轮分层重试浪费；
2. style op 的 opacity 以返回值判定失败 → 恒走 SetFilling 回退 → 2D 对象被双重填充（灰盘）。

**处置（已修）**：判定统一走 `ggbBridge.isScriptingCommand` 豁免（eval op / eval_raw /
visual.html 宿主三方同语义）；style opacity 的生效与否改用 `readOpacity`（getXML 实读
lineOpacity）验证，未生效才回退 SetFilling（同样实读验证），两路都无效才报「可放弃」。

**遗留不一致（本轮已修复）**：
- `dashed:false` 在 style op 是 no-op（`if (cmd.dashed)` 只处理 true），在 set_style 工具则有效（`dashed?1:0`）——**已对齐**为都落地。

### 模式 F：测试盲区 —— mock 层永远放行

**现象**：回放测试（63 用例）无法暴露任何非法属性命令——`mockGGB` 对 `/^Set\w+\s*\(/i` **无条件返回 true**。

**根因**：这是有意的取舍（属性命令失败语义在 bridge 层校验，mock 保持轻量），代价是：
- 臆造命令 `SetOpacity(...)` 在回放里畅通无阻，只能靠 `mustNotContainCommands` 静态断言兜；
- 本轮给静态预检加的所有规则在回放中走的是"拦截后不再进引擎"路径，mock 放行与否不再影响结果——
  **预检层把 mock 的盲区补上了**（拦截发生在进引擎之前，mock 恒放行变得无关紧要）。

## 3. 七层防御 × 属性命令覆盖矩阵

| 层 | 机制 | 属性命令覆盖（本轮前 → 本轮后） |
|---|---|---|
| ① 提示层 | prompts + RAG | ✅ 3D 禁令/值域/黑名单文本齐全（不变） |
| ② 自检层 | self_check | ⚠️ 只查「无 3D 禁用命令？参数个数匹配？」，无值域专项（不变，靠 ⑤ 兜底） |
| ③ 清洗层 | stripCodeFence | — 与属性命令无关 |
| ④ 校验层 | schema.ts Zod | ⚠️ style op 字段有值域（thickness 1~13 / opacity 0~1 / #RRGGBB）；eval 命令串只查黑名单+XSS → **Set* 值域裸奔**（⑤ 补上） |
| ⑤ 预检层 | commandValidate | ❌ 零 Set* 覆盖 → ✅ 3D 禁令 + 值域 + 色名 + 参数个数（mode 感知） |
| ⑥ 纠正层 | commandCorrect | ⚠️ paramCount + Levenshtein + 臆造映射可用；SetAnimating 震荡已修；mode 不感知（3D 拦截交 ⑤） |
| ⑦ 执行层 | ggbBridge / toolExecutor | ❌ style op 恒成功、失败不可见 → ✅ exists 预检 + dashed 对齐 + opacity 双失败可见；修复 prompt 补规则 10 |

## 4. 修复清单

### 本轮已实施

1. `commandValidate.ts`：`validateGGBCommand(cmd, mode?)` 属性命令专项——3D 禁令（`mode-forbidden`）、
   SetColor 值域/色名（`value-range`/`color-name`）、透明度 0~1、参数个数回退 KB（SetCoords 豁免）。
2. mode 透传：`ggbBridge.executeOne`、`toolExecutor.executeToolCall/dispatch`。
3. `ggbBridge.ts` style op：exists 预检；`dashed:false` 落地实线；opacity 生效判定（真实 GGB 走
   getXML 实读 lineStyle opacity /255，测试 mock 无 getXML 时信任返回值；未生效才回退 SetFilling，
   双双无效报「可放弃」）。
4. `ggbKB.ts`：补录 `SetAnimating`；清理 `buildHallucinationWarnings` 死过滤。
5. `prompts.ts`：buildCheckerPrompt 规则 10（0~1 浮点 ×255 换算 / 透明度可放弃 / 对象不存在先建后设）。
6. 测试：commandValidate.test.ts +16 例、ggbBridge.test.ts +4 例；单测 216/216、回放 63/63。

### 后续建议（未实施）

- `agentLoop` 熔断：对「对象 X 不存在」类属性错误做**同名重复计数**（同名错误第 3 次仍失败则强制跳过该样式），避免不熔断的循环。
- `diagnose()`（ggbBridge）补 Set*/style 启发式（当前只有 Vector/Slider）。
- 双路径容错统一：agent 工具 `SetStyleArgs` 用严格 `z.boolean()/z.number()`，JSON style op 用 BoolLike/NumLike 宽容——`dashed:"true"` 两条路径一过一拒。
- ggbKB `SetPointStyle` 标注仅 2D，但 `commands.ts` 白名单文本未标 `(仅2D)`——两处需对齐。
