# 大模型「按指定要求完成任务」能力方法调研 —— 与 AiGGB 实现对比技术报告

> 调研日期：2026-09-13。资料来源为各厂商官方 API 文档（逐条核对原文，链接见附录 A）；
> 本地实现对照 AiGGB 源码（文件：行号见附录 B）。
> 调研限制：Anthropic 文档当前区域不可访问未纳入；Qwen/SiliconFlow 未取到参数页原文，
> 预设中的候选模型不进入数字对照表。

---

## 1. 问题定义

「让大模型按指定要求完成任务」在工程上要对抗四类失效模式。AiGGB 的需求（自然语言 →
GeoGebra 命令 JSON / Agent 工具调用序列）恰好四类全占：

| # | 失效模式 | 在 AiGGB 中的表现 |
|---|---|---|
| ① | **格式漂移**：输出不合 schema（缺字段、多余 code fence、JSON 被截断） | Phase 2 命令 JSON 解析失败；Agent 工具参数 JSON 截断 |
| ② | **臆造**：编造不存在的 API/工具/参数 | 编造 GGB 命令名、`SetViewDirection` 等 3D 禁用命令、幻觉工具名 |
| ③ | **截断**：思考（reasoning）挤占输出预算，正文/工具调用为空 | deepseek-flash 单次推理可达 2.4 万字符，占满预算后空响应 |
| ④ | **语义偏差**：格式对了但画出来不对 | 命令全部执行成功但与题目要求不符（出框/遮挡/缺元素） |

## 2. 业界能力与方法盘点

### 2.1 解码期结构化约束（最硬的手段）

**OpenAI Structured Outputs（json_schema / strict 模式）**

- Function Calling 的 `strict: true` 官方定义为「确保函数调用可靠遵循 schema，而非 best
  effort」，并**建议始终开启**：
  > "Setting `strict` to `true` will ensure function calls reliably adhere to the function
  > schema, instead of being best effort. We recommend always enabling strict mode."
- strict 模式两项硬性要求：每个 object 层 `additionalProperties: false`；`properties` 里
  **所有字段都必须出现在 `required`**（可选字段用 `type: ["string", "null"]` 表达）。
- 限制：部分 JSON Schema 特性不受支持（根层 `anyOf`/`oneOf` 即 discriminatedUnion 形态不可用）。
- 非流式 `response_format: json_schema` 同样受这些 schema 限制约束。
- 另提供 **CFG（上下文无关文法）约束**：custom tool 可传 `grammar`（Lark 或正则，底层
  LLGuidance）对自由文本输出做解码期硬约束——这是目前 API 层面最强的输出约束形态。

**JSON mode（弱一级的约束）**

- DeepSeek 官方 JSON 模式指南明确三个前提：
  > "Include the word 'json' in the system or user prompt…"（prompt 必须含 json 字样并给示例）
  > "Set the max_tokens parameter reasonably to prevent the JSON string from being truncated midway."
  （max_tokens 需合理设置防 JSON 中途截断）
  并承认已知问题："the API may occasionally return empty content."（偶发空内容）
- OpenAI 文档同样警告 JSON 模式下若无 JSON 指示，模型可能「生成无休止的空白直到撞上
  token 上限」。
- **DeepSeek 不支持 json_schema**（AiGGB 实测 v4-flash 端点返回 400
  `response_format type unavailable`，仅支持 json_object）——同级厂商中约束能力最弱的一档。

**GLM**：OpenAI 兼容端点，支持 `response_format`；思考控制见 2.3。

### 2.2 工具调用协议（Function Calling）

- OpenAI 官方五步流程（请求带 tools → 收 tool_call → 本地执行 → 带 output 再请求 → 收
  最终回复/更多调用），并明确「应假设一次返回多个 tool_call」。
- **工具定义最佳实践**（官方）：
  > "Use enums and object structure to make invalid states unrepresentable."
  > "Keep the number of functions small for higher accuracy… Aim for fewer than 20 functions."
  > "Don't make the model fill arguments you already know."（已知参数由代码传入而非让模型填）
- `tool_choice`：`auto` / `required` / 强制单个函数 / `allowed_tools` 子集。
- **流式聚合**：tool_call 参数按 `delta` 增量返回，需按 output_index 累积合并成完整 JSON。
- **推理项回传**（官方）：
  > "For reasoning models like GPT-5 or o4-mini, any reasoning items returned in model
  > responses with tool calls must also be passed back with tool call outputs."
  （思考模型的多轮对话必须把 reasoning 内容原样回传，否则报错/失效）

### 2.3 思考（reasoning）与输出预算管理

这是 2025-2026 推理模型普及后新增长的核心约束点。**各家官方文档一致确认：思考 token 与
正文共享输出预算**，且各家表述精度差异很大：

| 厂商/模型 | 参数名 | 默认输出 | 硬上限 | 思考与预算的关系（官方口径） |
|---|---|---|---|---|
| **OpenAI**（GPT-5/o 系） | `max_output_tokens` | 因模型而异；**官方建议至少预留 25,000** | 因模型而异 | 最明确：reasoning token「不可见但按输出计费」，**计入 max_output_tokens 与 context window**；预算耗尽时 `status=incomplete`、`incomplete_details.reason=max_output_tokens`，**可能在任何可见输出产生之前耗尽**；`reasoning_effort` 默认 medium |
| **DeepSeek V4.1** | `max_tokens` | **非思考 8K / 思考 64K**（`reasoning_effort=max` 时 128K） | 384K（393216） | "input tokens 与生成 tokens 总长受 context 限制"；usage 返回 `completion_tokens_details.reasoning_tokens`；文档明确警告 `finish_reason="length"` 时 content 可能被部分截断 |
| **智谱 GLM** | `max_tokens` | 未明示（建议 ≥1024） | **131072**（GLM-4.6+/5.x 系 128K；4.5 系 96K） | 表述最弱：只有一句「思考过程会消耗额外的 Token，请合理规划使用」；usage **无 reasoning 拆分字段**；`thinking.type` enabled（默认）/disabled 二元开关，**GLM-5.3/5.3-FLASH 强制思考，传 disabled 直接报错**，5.2+ 才有 `reasoning_effort`（5.3 仅接受 max/high/low） |
| **Moonshot Kimi** | `max_completion_tokens`（**`max_tokens` 已标记弃用**） | K3 默认 131072 | **1048576（1M）** | 语义澄清最清楚：「此值为期望返回的 Token 长度，而非输入加输出的总长度」；**输入+该值超出上下文窗口直接 `invalid_request_error`**；截断时 `finish_reason="length"` |

DeepSeek 思考模式指南还有三个应用层细节：思考默认开启且 **默认 effort=high**；
**思考模式不支持 temperature/presence_penalty/frequency_penalty**——
> "Thinking mode does not support the temperature… Setting them will not trigger an error
> but will also have no effect."（设置不报错，但也完全无效）
工具调用轮「reasoning_content 必须在所有后续请求中完整回传」，否则 400（纯文本轮则
静默忽略、无需剥离）。

三个对应用层面的直接推论（AiGGB 全部踩过）：

1. **思考吃光预算 → 空响应**：OpenAI 原文「可能在可见输出产生之前耗尽」，DeepSeek 实测
   reasoning 占满预算后 content 与 tool_calls 双空。
2. **max_tokens 不是越大越好**：Kimi 明确「输入+输出超上下文直接报错」；DeepSeek 也有
   context 总长约束。申请量是上限不是计费量，但超 context 会拒单。
3. **截断检测必须依赖 `finish_reason`**：三家文档统一以 `finish_reason="length"`
   （OpenAI Responses 为 `incomplete_details.reason=max_output_tokens`）作为程序化信号。

### 2.4 失败自愈回路（validator-in-the-loop）

业界通行做法是**把校验器嵌进回路，将错误信息回喂给模型重试**，而不是简单重掷：

- **格式校验回喂**：JSON schema 校验失败 → 把原始输出 + 具体诊断（哪一行、哪个字段）作为
  新消息回喂 → 模型自修。这是所有 Agent 框架（LangChain、Function Calling cookbook 等）的标准循环。
- **环境反馈闭环（ReAct）**：工具执行结果（含报错原文）作为 observation 回喂，模型基于
  真实执行结果调整下一步。
- **LLM-as-judge / self-check**：用（通常是更便宜的）模型对产出与需求做核对，发现偏差
  反馈修正；多模态任务进一步用渲染截图做视觉核对。

### 2.5 Provider 差异适配（quirk 管理）

同一份 OpenAI 兼容协议在关键细节上各家不同，官方文档里可见的分歧点：

| 分歧点 | 各家行为 |
|---|---|
| max_tokens 字段名 | Kimi 已弃用 `max_tokens` → `max_completion_tokens`；OpenAI o 系也用后者 |
| 思考模式下的 temperature | DeepSeek 官方：thinking 模式不支持 temperature，设了静默无效；OpenAI 未见此声明 |
| 思考开关形态 | DeepSeek=`reasoning_effort`；GLM(4.5~4.7)=`thinking.type` 二元；GLM(5.2+)=`reasoning_effort`；OpenAI=`reasoning_effort` low/medium/high |
| reasoning 回传 | OpenAI GPT-5/o 系必须回传；GLM「保留式思考」（`clear_thinking:false`）要求「完整、未修改」原样回传；DeepSeek V4 多轮必须回传否则 400 |
| json_schema 支持 | OpenAI/GLM/Kimi 支持；DeepSeek 仅 json_object |
| 单轮并行工具数 | OpenAI 提供 `parallel_tool_calls` 开关；DeepSeek 无开关但实测单轮 >4 个 tool_calls 会丢失后半（需客户端自限） |

## 3. AiGGB 实现对照

### 3.1 总体架构

AiGGB 用两条回路覆盖「按指定要求完成任务」：

- **两阶段流水线**（`pipeline.ts`）：Phase 1 精炼（意图→规格，用户确认）→ Phase 2 编译
  （规格→命令 JSON + `self_check` 自检报告）→ RAG 纠正 → 执行 → 失败修复回路（≤2 次）
  → 满足度评估。
- **Agent 回路**（`agentLoop.ts`）：ReAct 工具调用循环（≤30 迭代）+ 空响应截断重试 +
  状态核对钩子（文本快照 + 截图视觉双路 judge）。

### 3.2 逐项对照矩阵

| 失效/需求 | 业界方法 | AiGGB 实现 | 代码位置 |
|---|---|---|---|

| ① 格式漂移（已发生） | 校验错误回喂重试 | `chatWithFormatRetry`：`AISchemaError` 携带 raw+detail，把原输出与诊断作为新消息回喂，≤`MAX_FORMAT_RETRY=2` 次 | `pipeline.ts:568-596` |

| 项 | 厂商官方 | AiGGB | 评价 |
|---|---|---|---|
| 非思考默认输出 | DeepSeek 8K；Kimi K3 128K；OpenAI 因模型而异 | **16384** | 高于 DeepSeek 默认，合理 |
| 思考默认输出 | DeepSeek 64K（effort=max 128K）；OpenAI 建议预留 ≥25K | **32768** | 与 OpenAI 建议同量级；低于 DeepSeek 默认（靠降档+扩容补偿） |

| 截断重试扩容 | —（业界无标准做法） | **×2 + 降档 low** | 自研且有效；唯一实现「重试必须改变条件」的路径 |

### 3.4 与业界一致或超出常规的设计（亮点）

1. **strict:false + 简化骨架**（`AI_RESPONSE_JSON_SCHEMA` 只约束 op 枚举骨架）是对官方
   「strict 模式不支持部分 JSON Schema 特性」的正确回应——Zod discriminatedUnion 无法直接
   翻译成合规 strict schema，骨架约束 + 应用层 Zod 细校验是等效工程折衷。
2. **截断重试「改变条件」原则**：`agentLoop.ts:54-57` 注释明确「同参数重试必然同样截断」，
   扩容+降档+指令三件套与 OpenAI「提高 max_output_tokens / 降 reasoning_effort」的官方
   建议方向一致，属于业界少见的成熟实现。
3. **状态核对双路合并**（文本快照 judge + 截图视觉 judge）超出常规 LLM-as-judge：对
   「渲染正确性」这一几何/物理特有维度补上了视觉审查，且失败均不阻断。
4. **`chatRaw` json 模式 4096 兜底**是 DeepSeek 官方「max_tokens 防截断」建议的直接落实。

## 4. 差距与改进建议（按优先级）

> F1–F7 均已在代码中核实，行号见附录 B。

**F1（P1）格式重试回路存在与 agentLoop 同源的缺陷：重试不改变输出预算。**
`chatWithFormatRetry`（`pipeline.ts:575-590`）捕获 `AISchemaError` 后**原参数重试**。若根因
是 JSON 被截断（DeepSeek 默认仅 8K 非思考预算时的大命令 JSON），同参数重试必然再次截断
——这正是 `agentLoop.ts:54-57` 修过的「情况 2」缺陷在非流式路径的残留。建议：截断时
（`finish_reason="length"`，见 F7）在重试前扩预算（如 `maxOutputTokens×2`），或至少在重试
消息中注入「请压缩输出规模（减少命令条数）」。

**F2（P1）GLM 截断降档实际无效，且注释与代码不符。**
`TRUNCATION_RETRY_REASONING="low"`（`agentLoop.ts:59-62`）经 `buildThinkingParam`（`aiClient.ts:173-183`）
对 GLM 落为 `thinking.type:"enabled"`——GLM 的二元开关**没有 low 档**，降档等于原样；而
`agentLoop.ts:61` 注释声称「GLM 经 buildThinkingParam 落为 disabled」，与代码行为相反。
按新文档 GLM-5.2+ 已支持 `reasoning_effort`（GLM-5.3 接受 max/high/low），建议
`buildThinkingParam` 按模型版本对 GLM 直发 `reasoning_effort`，使降档真正生效。

**F3（P2）GLM-5.3 强制思考：「关闭思考」会 400。**
官方明确 GLM-5.3/5.3-FLASH「thinking.type 传 disabled 将会报错」。当前 `buildThinkingParam`
对一切 GLM 在关闭档发 `thinking.disabled`，用户选 GLM-5.3 + 设置「关闭思考」即触发报错。
建议按模型版本分支：5.3 系不发 disabled（改发 `reasoning_effort:"low"` 或静默忽略关闭请求并在 UI 提示）。

**F4（P2）Kimi 的 `max_tokens` 已弃用。**
quirks 已声明 `maxTokensField` 字段（`aiClient.ts:98-99`）但 `getProviderQuirks` **从未返回它**，
所有 provider 均发 `max_tokens`。Kimi 官方已标记弃用（新参数 `max_completion_tokens`，
K3 默认 131072/上限 1M）。建议为 moonshot 加 `maxTokensField: "max_completion_tokens"`。

**F8（P2）DeepSeek 思考模式下 `agentTemperature=0.05` 是无效参数。**
官方 thinking mode 指南明确：思考模式不支持 temperature，「设置不报错但无效果」。DeepSeek
V4 默认开启思考（默认 effort=high），因此 `getProviderQuirks` 里「低温度减少 tool name
幻觉」的 quirk（`aiClient.ts:126`）在默认配置下**不起作用**，仅在用户显式关闭思考
（`reasoningEffort:"none"`）时才生效。防 tool name 幻觉实际依赖的是 RAG 纠正层与
`maxToolsPerTurn` 限制。建议：更新该 quirk 注释说明生效条件，避免后续调参误判。

**F5（P3）`MAX_OUTPUT_TOKENS=65536` 钳制偏保守。**
DeepSeek 上限 384K、GLM 128K、Kimi 1M。截断重试扩容 ×2（32768→65536）后恰好顶到钳制值，
更大规模的构造任务失去扩容空间。建议放宽到 131072（对齐 GLM 硬上限），或把钳制值放进
quirks 按 provider 配置；同时注意 Kimi「输入+max_tokens 超上下文直接报错」的约束，扩容时
应结合 `contextWindow` quirk 做上限折算。

**F6（P3）`chat()`/`chatRaw()` 不检查 `finish_reason`，截断被伪装成格式错误。**
`chat()` 只读 `message.content` 与 `usage`（`aiClient.ts:450-486`），非流式路径的截断
（DeepSeek 文档明确警告 `finish_reason="length"` 时 content 部分截断）只能以 JSON 解析失败
的形态进入 F1 的格式重试，根因不可见。建议 `chat()` 透传 `finish_reason`，截断时抛带标记
的 `AISchemaError`（detail 注明「输出因长度限制被截断」），让重试与用户提示有据可依。

**F7（P3，演进项）GLM 交错思考的 reasoning 回传。**
GLM「保留式思考」（`clear_thinking:false` + 工具调用）要求「完整、未修改」回传
`reasoning_content`，与 OpenAI GPT-5 的要求同构。当前 GLM `mustRoundtripReasoning=false`
在默认 `clear_thinking=true` 语义下正确；若未来启用 GLM 保留式思考/交错思考需翻转该 quirk
（机制已存在，改动一行 + 测试）。

---

## 5. 结论

- AiGGB 对「按指定要求完成任务」的对抗体系（七层防漂移 + 截断三件套 + 双路 judge）在
  **方法论上与业界最佳实践同构**，多处实现（strict schema 折衷、SSE 聚合、reasoning 回传、
  DeepSeek json 模式 max_tokens 兜底）与官方文档要求精确对齐，截断自愈回路甚至是业界少见的
  成熟度。
- 主要差距集中在 **2026 年新模型行为跟进**（GLM-5.x 强制思考与 reasoning_effort 分化、
  Kimi 参数更名、DeepSeek 思考模式温度失效）和 **非流式路径的自愈闭环不对称**（agentChat
  有截断检测，chat/chatRaw 没有；格式重试不改预算）。F1/F2 一处改动即可把已验证的截断
  自愈能力补齐到全部调用路径。
